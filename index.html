Guia do Kit IA para Copilot

Kit de pastas prontas para o GitHub Copilot no VS Code trabalhar em passos pequenos, seguindo o padrão do seu projeto.

O que é o kit

O kit é um conjunto de pastas prontas que você copia para a raiz de um repositório. Ele ensina o Copilot a trabalhar do seu jeito: passos pequenos, padrão do projeto, design system do projeto e sem fazer commit por você. Não instala nada: são só arquivos de texto, que o Copilot lê.

O que o kit entrega

  • Regras fixas do projeto que o Copilot lê em todo chat (stack, comandos, convenções, idioma, responsividade).
  • Comandos / para cada etapa: explicar, especificar, planejar, implementar, revisar, auditar.
  • Agentes com papéis definidos: implementador, revisor, professor e auditor.
  • Regras por tipo de arquivo, aplicadas sozinhas em código de front-end e em testes.
  • Um gate (scripts/gate.sh) que roda lint, typecheck e testes ao fim de cada passo.
  • Um modelo de spec para transformar o seu briefing em critérios verificáveis.

O que o kit não faz

  • Não lê board nem PBI: você escreve a demanda no prompt.
  • Não faz commit nem push: os commits são seus.
  • Não roda o app nem mede performance sozinho: quem confirma isso é você, no navegador, com a aba Performance e o console.

Idioma

Os arquivos do kit estão em inglês, porque a IA gera código melhor assim. Cada arquivo tem um comentário em português no topo dizendo o que faz. O Copilot responde em português do Brasil.

Instalar o kit em um projeto

Instalar é só copiar três pastas para a raiz do repo, a pasta onde fica o package.json.

  1. Clone este repositório (ou baixe o zip) em uma pasta temporária, fora do projeto.
  2. Dentro dele há .github, docs e scripts. A .github é oculta: no Finder, aperte Cmd+Shift+. para ver. No VS Code ela aparece normalmente.
  3. Copie as três pastas para a raiz do repo. Se o repo já tem uma .github, junte o conteúdo e não substitua a pasta.
  4. Se o repo já tem um .github/copilot-instructions.md, não sobrescreva. Guarde o antigo e copie os trechos úteis para o novo.
  5. Abra o repo no VS Code e confirme que o Copilot Chat está ativo. Digite / no chat: os comandos do kit devem aparecer na lista.

Teste pessoal, sem afetar o time

Crie uma branch sua (git checkout -b teste-kit-ia) e não faça commit das pastas do kit. Se não gostar, apague a branch. Para manter o kit local sem rastrear, adicione .github/prompts, .github/agents, .github/instructions, docs/specs e scripts/gate.sh ao arquivo .git/info/exclude do repo; ele funciona como um .gitignore só seu.

Se os comandos / não aparecerem: o formato de prompts e agentes depende da versão do VS Code e do Copilot. Atualize os dois e reinicie o VS Code. Se ainda não aparecer, anote a versão e o que aparece, e ajuste o kit com essa informação.

Primeiro uso em cada projeto

Faça isso uma vez por projeto, em chats novos, nesta ordem.

  1. /setup-project: preenche o .github/copilot-instructions.md. Ele lê o package.json e o repo, descobre o nome do pacote do design system, os comandos e a stack, pergunta só o que faltar (normalmente se o projeto é ferramenta interna ou produto externo) e edita apenas os campos FILL IN. Confira o que ele preencheu, principalmente o nome do design system e o comando de teste.
  2. /map-project: lê o repo e descreve os padrões reais (pastas, nomes, forma de chamar API, como os testes são escritos) e lista inconsistências. Cole o que estiver certo na seção Conventions do copilot-instructions.md. Não edita nada.
  3. /map-design-system: lê o pacote do design system em node_modules e gera docs/design-system.md com os componentes, props e tokens. Confira 2 ou 3 componentes que você conhece. Refaça quando o design system atualizar.
  4. bash scripts/gate.sh no terminal: confirma que lint, typecheck e testes rodam. Se o script test do projeto for modo watch (--watch, ou vitest sem run), ajuste antes ou o gate trava.

Preenchendo o copilot-instructions.md à mão

Se preferir não usar o /setup-project, abra o arquivo e troque o que estiver entre <...> ou marcado com FILL IN. O mínimo: nome do pacote do design system (veja dependencies no package.json), comandos de instalar e rodar (npm install e geralmente npm run dev ou npm start), o tipo de produto e uma linha dizendo o que o projeto é. Procure FILL IN com Cmd+F para ver se sobrou algum. Apague as linhas que não souber preencher, para a IA não tratar <...> como instrução.

Fluxo de uma tarefa

Uma tarefa, um chat. Cada etapa produz algo que você lê e aprova antes de seguir.

  1. Briefing. Escreva a demanda em 3 ou 4 linhas: o que fazer, onde, o que não mexer. Você escreve; a IA não lê board nem PBI.
  2. /explain (opcional). Use quando não souber como resolver. Ele explica a área, aponta riscos, propõe 2 ou 3 caminhos e faz 3 perguntas para você conferir se entendeu. Não edita nada.
  3. /spec. Transforma o briefing em docs/specs/<nome>.md com objetivo, critérios de aceite, fora de escopo, casos de borda (erro, vazio, carregando, responsivo) e dúvidas em aberto. Leia, corrija e responda as dúvidas antes de seguir.
  4. /plan. Preenche o plano da spec em passos pequenos, um passo por commit, dizendo onde cada estado vai morar. Não implementa. Aprove ou peça ajustes.
  5. /implement-step. Implementa um passo, roda o gate e para. Veja o diff (git diff), teste no navegador e só então faça o commit, você mesmo. Repita para o próximo passo.
  6. /review em chat novo. Escolha o agente reviewer, aponte a spec e deixe ele revisar o diff. Um chat novo evita que a IA defenda o que ela mesma escreveu.
  7. Revisão humana. Você lê o código final. A IA ajuda, mas você responde por ele.

Mudar código que já existe

No lugar de /implement-step direto, comece com /change-existing-code. Ele mapeia quem usa a área, propõe um teste do comportamento atual quando não há teste e faz o menor diff possível.

Tarefa pequena

Para ajustes simples (cor, texto, margem) pule spec e plan e vá direto ao /implement-step com a descrição. Use o fluxo completo quando a demanda tiver regra de negócio, vários arquivos ou risco de quebrar algo.

Na prática: do pedido até o commit

Exemplo completo com uma demanda inventada: "na tela de ordens, quando a lista vem vazia, mostrar uma mensagem e um botão Atualizar". Troque pelos nomes do seu projeto. O texto em bloco é o que você digita.

Passo 1. Entender (só se você não souber por onde começar)

Chat novo, agente explainer:

/explain Tela de ordens (src/features/orders). Preciso mostrar um estado vazio quando não há ordens. Como a lista é carregada hoje e onde esse estado entraria?

Leia a resposta e confira se os arquivos citados existem. Responda as 3 perguntas finais para você mesmo; se não souber, peça "explique melhor o ponto X".

Passo 2. Criar a spec

/spec Na tela de ordens, quando a lista vem vazia, mostrar uma mensagem "Nenhuma ordem encontrada" e um botão "Atualizar" que recarrega a lista. Usar componentes do design system. Não mexer na tabela, nem nos filtros, nem na chamada de API.

A IA cria docs/specs/orders-empty-state.md. Leia: o objetivo está certo? Os critérios de aceite são verificáveis? "Fora de escopo" tem o que você pediu? Responda as "Dúvidas em aberto", editando o arquivo ou dizendo no chat: "As dúvidas: 1) sim, o botão recarrega; 2) a mensagem é só em português."

Passo 3. Planejar

/plan docs/specs/orders-empty-state.md

A IA escreve o plano em passos pequenos no fim da spec. Cada passo cabe em um commit? Tem o passo dos testes? Se estiver grande demais, diga "quebre o passo 2 em dois". Só siga quando concordar.

Passo 4. Implementar, um passo por vez

Troque para o agente implementer:

/implement-step passo 1

A IA edita, roda bash scripts/gate.sh e responde com os arquivos mudados e o resultado. Você faz:

  1. git diff (ou a aba Source Control do VS Code) e lê o que mudou.
  2. Abre a tela no navegador e vê funcionando, em 1280, 1440 e 1920px.
  3. Se estiver bom, você faz o commit, em português: Adiciona estado vazio na lista de ordens.
  4. Se não estiver, diga o que está errado ("o botão ficou fora do padrão do design system, use o componente Button") e peça para corrigir antes de seguir.

Depois: /implement-step passo 2, e assim por diante.

Passo 5. Revisar em chat novo

Abra um chat novo e escolha o agente reviewer:

/review docs/specs/orders-empty-state.md

Ele lê o diff e lista problemas por gravidade (bloqueia, deveria corrigir, sugestão). Para cada "bloqueia", volte ao agente implementer em outro chat e peça a correção, citando o problema. Rode o /review de novo até não sobrar bloqueio.

Passo 6. Fechar

Leia o código final, rode o gate e o app uma última vez, e abra o PR do jeito que o seu time já faz. Se a tarefa ficou longa e você precisa trocar de chat no meio, rode /context-summary e cole o resumo no chat novo.

Quanto cada passo gasta. O fluxo completo usa várias mensagens e gasta mais do seu limite. Se a demanda for pequena (trocar uma cor, um texto), pule os passos 1 a 3 e use só /implement-step Trocar o texto do botão X para Y em src/....

Receitas: "preciso fazer X, como proceder"

Como escrever bons pedidos

  • Diga onde: pasta ou arquivo. Sem isso a IA procura em tudo e erra mais.
  • Diga o que não mexer.
  • Diga o resultado esperado em 1 ou 2 frases verificáveis ("aparece a mensagem X quando a lista tem 0 itens").
  • Um pedido, uma mudança. Se tiver duas, faça duas tarefas.
  • Se a resposta vier errada, corrija com precisão ("o arquivo certo é X, não Y") em vez de repetir o pedido.

Agentes

Os agentes aparecem no seletor do chat do Copilot. Um agente muda o papel da IA durante toda a conversa.

AgentePapelEdita?Quando usar

Dica de segurança

Os agentes reviewer, explainer e auditor não devem editar nada. Se o seletor de ferramentas do VS Code permitir, restrinja as ferramentas deles a leitura e busca. Assim a regra não depende só da instrução em texto.

Prompt ou agente?

O prompt (/comando) é uma receita para uma tarefa. O agente é um papel que dura a conversa toda. Eles se combinam: escolha o agente auditor e rode /audit-project.

Regras automáticas

Três arquivos são lidos sem você pedir. Eles guiam tudo o que a IA escreve.

ArquivoQuando valeO que contém
.github/copilot-instructions.mdEm todo chatProjeto, comandos, convenções, idioma, jeito de trabalhar, padrões e precedência, responsividade, o que nunca fazer
.github/instructions/frontend.instructions.mdEm arquivos .ts, .tsx e .cssDesign system, estado, listas, effects, segurança do DOM, Context, performance, acessibilidade, responsividade
.github/instructions/testing.instructions.mdEm arquivos de testeTestar comportamento, RTL, mocks do Jest, Playwright

O que as regras de front-end forçam

  • Estado fica perto de quem usa e nunca é mutado. Não inicializar useState a partir de props.
  • key estável e única, nunca o índice em lista dinâmica.
  • useEffect só para efeito real, com cleanup e AbortController. Nada de estado derivado em effect.
  • Sem {...props} solto em elemento DOM e sem HTML não sanitizado.
  • Performance: medir primeiro; mover o estado para baixo antes de memoizar; checar se o projeto usa React Compiler antes de colocar memo manual.

O que as regras de teste forçam

  • Testar o que o usuário vê, com getByRole. Cobrir fluxo principal, erro, vazio e carregando.
  • Mockar só a borda (API, rede, timers). Preferir implementação real.
  • Sem .only e sem .skip sem motivo. Cobertura é guia, não meta de 100%.

Quando o padrão do repo diverge das regras

Vale a seção "Standards and precedence" do copilot-instructions.md, nesta ordem: a spec, o padrão alvo que você definiu para código novo, o padrão local do código ao redor e, por fim, as regras gerais. Código novo segue o padrão alvo; código antigo mantém o padrão local até uma spec pedir refatoração. Nunca misture dois padrões no mesmo arquivo. Para adotar um padrão novo de propósito (biblioteca, estrutura, convenção), diga isso no prompt: a IA lista os arquivos afetados e migra uma área por vez, com os testes verdes a cada passo.

Se a IA estiver ignorando regras

Regras demais competem por atenção. Corte as seções menos úteis do frontend.instructions.md (por exemplo Context e Performance) e veja se melhora.

Auditoria e performance

/audit-project

Use o agente auditor em chat novo e escreva depois do comando a pasta que quer auditar (por exemplo src/features/orders). Sem pasta, ele tenta o projeto inteiro, mas num repo grande o relatório fica raso. Comece por uma feature que você conhece bem, assim você consegue dizer se ele acertou.

Ele olha, nesta ordem: estrutura, estado e dados, renderização e performance, uso do design system, TypeScript, testes, acessibilidade, responsividade e segurança. A resposta vem em português com:

  • Resumo: saúde geral (boa, ok ou arriscada) e o motivo principal.
  • O que está bom: só pontos fortes reais, com evidência.
  • O que está ruim: tabela com problema, arquivo e linha, e gravidade.
  • Erros que podem acontecer: o sintoma concreto de cada problema, por exemplo "a lista perde o foco do input ao ordenar por causa de key com índice".
  • Responsividade: como está contra o alvo do produto, com as correções mais baratas primeiro.
  • O que melhorar: ganhos rápidos primeiro, refatorações maiores depois.
  • Não confirmado: o que ele não conseguiu verificar e a quem perguntar.

Como julgar o relatório

  • Desconfie de qualquer afirmação sem arquivo e linha.
  • A auditoria só lê código. Responsividade e performance precisam ser confirmadas por você: abra a tela em 1280, 1440 e 1920px e meça com a aba Performance do navegador ou com o componente Profiler do React.
  • Se algo parecer exagerado, pergunte ao auditor a evidência.

Começando pela auditoria

  1. Copie o kit numa branch sua e rode /setup-project (e /map-design-system, se puder).
  2. Audite uma pasta que você conhece.
  3. Escolha 2 ou 3 achados úteis e baratos de corrigir. Cada achado vira uma tarefa pequena: /spec Corrigir o problema 2 da auditoria: <cole o achado com arquivo e linha>. Não mexer em <o que fica de fora>.
  4. Siga o fluxo normal e faça um achado por vez, com um commit seu em cada passo.

/perf-review

Para lentidão ou re-renders demais. Ele não sai mudando código: diz como medir antes e depois, acha onde o estado vive, ordena as causas prováveis e propõe as correções na ordem certa. Mover o estado para baixo ou isolá-lo em um componente pequeno vem antes de memo, useMemo e useCallback.

Como medir sem instalar nada: a aba Performance do Chrome (tarefas longas aparecem em vermelho), o componente <Profiler> nativo do React com um console.log temporário no onRender, ou contagem de renders com console.log (o Strict Mode dobra a contagem em dev). Remova o código de medição antes de finalizar e não faça commit dele. Traga os números para ele trabalhar com dados reais.

Contexto, limite de uso e boas práticas

Um chat por tarefa

Chats longos acumulam contexto, ficam lentos e confusos. Abra um chat novo a cada tarefa e, principalmente, para o /review. Se precisar continuar uma tarefa em outro chat, rode /context-summary e cole o resumo no chat novo.

Limite de uso

O Copilot pode contar por requisição ou por crédito, dependendo do plano da sua empresa. Confira no seu plano e no painel de uso, e meça o gasto de cada comando no primeiro teste. O fluxo completo gasta mais que um prompt solto. Para economizar:

  • Use o fluxo completo só em demandas com regra de negócio, vários arquivos ou risco.
  • Em ajustes pequenos vá direto ao /implement-step.
  • Aponte pastas e arquivos em vez de pedir "o projeto inteiro".
  • Rode /setup-project, /map-project e /map-design-system uma vez por projeto, não a cada tarefa.
  • Uma tarefa por chat. Chats longos carregam o histórico todo a cada mensagem.

Gate (o "hook")

O scripts/gate.sh faz o papel dos hooks: roda lint, typecheck e testes, pulando o que o projeto não tem, e para no primeiro erro. A IA é instruída a rodá-lo ao fim de cada passo e só dizer "terminei" se passar. Você também pode rodá-lo no terminal: bash scripts/gate.sh. Funciona no zsh do Mac, porque o comando chama o bash explicitamente.

Testes

O comando de teste é npm run test, que roda uma vez. A IA nunca deve rodar o modo watch, porque ele não termina e trava o agente. Confira no package.json que o script test não é watch.

Commits

Você faz todos os commits, em português, curtos e no imperativo. Se quiser uma sugestão, peça: "sugira uma mensagem de commit".

Loops de revisão

O ciclo é implementar, gate, revisar em chat novo, corrigir. Quando o reviewer apontar algo em "bloqueia", corrija e rode o /review de novo em outro chat.

Responsividade por tipo de produto

O alvo depende do produto. Defina isso no copilot-instructions.md (o /setup-project pergunta).

TipoAlvoO que a IA deve garantir
Ferramenta internaDesktop, de 1280px a 1920px ou mais, zoom até 150% e janela redimensionadaSem sobreposição, texto cortado ou scroll horizontal acidental; tabelas, painéis e barras que se adaptam quando a largura diminui
Produto externoMobile-first e também desktopTudo acima, mais ajuste em 360px e alvos de toque de pelo menos 44px

Regras de código

  • Flex e grid, unidades relativas (rem, %, fr, clamp) e min-width ou max-width, em vez de larguras fixas em px.
  • Breakpoints vêm dos tokens do design system, se existirem. Não inventar novos.
  • Sem height: 100vh com overflow escondido; use min-height e regiões com scroll.

Em código antigo

A IA não reescreve o layout de uma tela mal resolvida a menos que a spec peça. Ela apenas aponta a lacuna no relatório, para uma demanda pequena não virar uma refatoração grande.

Antes de dizer que terminou

Abra a tela em 1280, 1440 e 1920px (e 360 e 768px no produto externo). A IA não enxerga o resultado, então essa checagem é sua.

Roteiro de teste, do zero até a auditoria

Use uma branch descartável e uma tarefa de mentira. Nada disso vai para o time.

Preparação (10 min)

  1. git checkout -b teste-kit-ia na raiz do repo.
  2. Copie .github, docs e scripts do kit para a raiz.
  3. Rode /setup-project no chat do Copilot e confira o que ele preencheu.
  4. Rode bash scripts/gate.sh no terminal. Se der erro, guarde a saída.

Mapear o projeto (15 min)

  1. Em chat novo, /map-project. Compare com o que você sabe do repo.
  2. Em outro chat novo, /map-design-system. Confira o docs/design-system.md com 2 ou 3 componentes que você conhece.

Tarefa de mentira (30 a 40 min)

  1. Escolha algo pequeno e seguro: escrever testes de um componente sem teste é o que menos arrisca. Outras opções: estado vazio numa lista ou melhorar um loading.
  2. /explain com a demanda. Veja se os arquivos citados existem.
  3. Briefing de 3 ou 4 linhas e /spec. Leia a spec.
  4. /plan, e se ficar bom, /implement-step no primeiro passo.
  5. Veja o diff, rode o gate, e faça o commit ou descarte.
  6. Chat novo, agente reviewer, /review apontando a spec.

Auditoria (10 min)

  1. Chat novo, agente auditor, /audit-project com uma pasta que você conhece.
  2. Confira o relatório: tem arquivo e linha? Tem "Não confirmado"? Os pontos de responsividade fazem sentido no navegador?

No final

  1. Anote o que funcionou, o que o Copilot errou ou ignorou e se algum comando não apareceu.
  2. Para limpar: git checkout - e git branch -D teste-kit-ia.

Versão mínima. Se faltar tempo: passos 1 a 6, depois 13 e 14.

Limites honestos

  • O kit é uma primeira versão e não foi validado em muitos projetos reais. Ajuste com o que você observar.
